# 技术标投标文件生成

## When to Use

当用户要求依据招标文件生成一份或多份中文技术标、运维服务方案或投标 DOCX 时使用本技能。

## 适用范围

用于根据招标文件生成中文技术标，尤其适用于政府采购、运维服务、弱电与显示屏项目。交付物应是可直接编辑和审核的 DOCX，而不是仅在聊天中输出提纲。

## 固定工作流程

1. 先确认工作目录、招标文件和输出目录。文件名、项目编号、服务期限、预算、交付截止时间等身份信息必须从招标文件读取，不凭记忆补写。

2. 优先读取原始文件。若招标文件是 `.doc` 而 OfficeCLI 不支持，使用 macOS `textutil -convert txt -stdout` 提取文本到 Hermes scratch，再基于完整文本生成；不要把转换后的文本当成最终交付文件。若存在 `.docx`，用 `officecli view <file> text`、`outline` 和 `stats` 检查内容与结构。

3. 先提取硬性要求形成响应清单，至少覆盖服务范围、设备与点位、维护周期、故障响应、人员配置、质量考核、服务期限、预算限制、交付格式和资格限制。把“招标文件明确要求”“我方拟定措施”“需现场确认”分开，证据不足时使用条件性表述，不写成无条件满足。

4. 用户要求多版本时，使用 `delegate_task` 并行生成三份真正差异化的版本。为每个 agent 指定不同主线，例如体系化闭环、现场工单与故障诊断、公共服务与风险治理；共享招标文本路径和输出目录，但使用不同文件名，禁止互相覆盖。主 agent 负责最终审核，不直接把子 agent 的自报结果当成已验证事实。

5. 每份技术标至少包含“维保整体服务方案”“质量保障措施及服务承诺”“管理机构及管理水平”“突发事件处理应急预案”四个章节，并按招标文件要求扩展子章节。内容应写成投标人可执行的服务方案，包含流程、责任、记录、闭环、验收和沟通机制，而不是空泛口号。

6. 当用户要求“不使用项目符号”时，全文不得使用项目符号、圆点列表、编号列表或类似短语堆叠。使用正式章节标题、连续段落和必要的表格；表格用于对照、时序、职责或响应矩阵，不用表格伪装项目符号列表。章节编号可以保留，除非用户连章节编号也禁止。

7. 生成 DOCX 后必须验证。至少检查文件存在、能被 `officecli view <file> text` 读取、`officecli validate <file>` 通过，并搜索提取文本确认四个必需章节存在、项目符号标记没有意外出现。必要时再用 `officecli view <file> issues --type structure` 检查结构问题。

8. 最终交付前横向比较三份文件的项目名称、编号、服务期限、关键硬性要求和四个章节。确认版本不是只替换标题，而是在方案逻辑、流程组织和风险重点上真正不同。报告未确认或存在偏差的内容，不把“文件已生成”夸大为“已满足全部招标要求”。

## 文档写作规则

使用简体中文、正式投标语体，先写服务目标和响应逻辑，再写实施方法、人员责任、记录表单、考核闭环和应急升级。涉及厂家、型号、时限、数量、点位或承诺时，优先逐项回指招标文件；文件没有给出确定值时写“我方拟按合同及现场确认执行”，并标注需要采购人确认的边界。

技术标应保持公司主体、项目名称和编号一致。不要自行补写投标人名称、联系人、资质证书编号、品牌型号或法定响应时限；这些信息缺失时留出可替换字段或使用条件性表述。

## 常见陷阱

不要把招标公告的报名或开标信息误写成运维服务承诺，因为两者的法律作用不同。

不要为了显得完整而杜撰设备数量、响应分钟数、备件库存、驻场人数或考核分值；这些数字会变成投标承诺并可能造成偏差。

不要让三个 agent 使用同一套通用模板只改章节名；差异化应体现在服务模型、现场流程、管理机制和应急推演上。

不要在子 agent 完成后跳过主 agent 的文件级验证；子 agent 的“已生成”“已验证”只是自报，必须重新读取或用工具检查交付物。

不要覆盖原始招标文件或已有投标版本；新版本使用独立输出目录和明确文件名，便于横向比对与回滚。

## 工具速查

```bash
# .doc 提取为文本
textutil -convert txt -stdout input.doc > "$TMPDIR/bid.txt"

# DOCX 检查
officecli view output.docx text --max-lines 300
officecli view output.docx outline
officecli view output.docx stats
officecli validate output.docx
```
