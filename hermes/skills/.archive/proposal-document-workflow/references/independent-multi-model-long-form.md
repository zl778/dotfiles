# 独立多模型长篇投标编制参考

## 适用场景

同一招标项目需要由不同 Profile/模型分别生成 B、C 等差异化技术标，最终由主 Agent 审核并生成 docx。目标不是同一底稿的同义改写，而是相同事实边界下的独立结构、表达和方法论。

## 先冻结约束

在派发前建立一份独立编制简报，至少写明：

- 禁止读取或复用旧版 B/C 正文；只能读取招标文件、评审要求、对应格式规范和事实简报。
- 字数口径：明确正文段落、标题、表格是否计入；封面和目录是否排除。
- 版本差异：B 可偏评审矩阵、工程管理、检查清单和项目符号；C 可偏技术架构、运行机制、故障闭环和持续优化。
- C 的标题层级上限、是否执行暗标匿名限制、是否允许图表/项目符号。
- 禁止商务业绩、报价、价格评审和未提供的品牌、型号、数量、姓名、现场实测事实。

用户给出新的字数或格式口径后，应覆盖旧简报，不得继续沿用旧限制。

## 分块生成

一次性要求模型生成 12,000+ 字并同时制作 docx 容易产生空文件、半成品或只写检查脚本。优先采用：

1. 每个模型分 8–12 个章节块，每块约 800–1,300 个中文字符。
2. 每块单独写入临时 Markdown 文件，要求只输出正文，不输出推理、状态、session_id 或工具说明。
3. 每块完成后独立检查非空、字符数和污染文本，再拼接。
4. 某块失败时只重试该块，不回退到旧 B/C 正文。
5. 拼接后按“正文段落 + 标题 + 表格文字”的最终口径统计，不让封面和目录进入统计。

短块调用稳定、长块调用失败时，应将长任务拆细；不能把空输出当成完成，也不能用主 Agent 自己扩写后宣称是模型独立稿。

## 差异化设计

保持事实一致，但至少在以下三项上产生实质差异：

- 章节组织：B 用评审因素→响应措施→交付物→核验方式；C 用系统链路→运行机制→故障闭环→持续优化。
- 运维方法：B 强调责任矩阵、检查清单、故障分级和可评分证据；C 强调状态采集、根因分析、验证和知识沉淀。
- 表达方式：B 可以使用项目符号和响应表格；C 使用连续技术叙述、流程和少量结构化表格。

只更换标题编号、同义词或统一补充段落，不算差异化。

## Provider/模型派发前检查

Profile 的 `model.provider`、`model.base_url`、认证来源和模型名称必须相互匹配。常见错误是把原生 DeepSeek/NVIDIA provider 指向 SiliconFlow endpoint，导致 401；或用 `custom` provider 却没有绑定 custom endpoint 的 API key。派发前用每个 Profile 的短调用验证真实配置，成功后再启动分块任务。若切换到原生 endpoint，应记录实际 provider/model，不要在交付中声称使用了未实际调用的模型。

## 主 Agent 验收

最终 docx 生成前后都要独立检查：

- 文件由本轮新块组成，未混入旧稿；
- 字数按用户口径统计；
- 标题层级、编号和格式符合 B/C 规范；
- 必须评分因素和技术场景逐项存在；
- 商务、业绩、报价、价格评审内容不存在；
- 项目符号和表格数量与版本约束相符；
- 关键承诺用明确原文响应，例如人员流失率不高于 10%、30 分钟响应、4 小时到场、12/48 小时修复；
- python-docx 重开成功；
- LibreOffice 或其他渲染器实际转换成功。

发现“报价”这类词时，要检查它是否出现在排除性说明中；正式技术正文中即使是“本部分不含报价”也可能触发商务隔离检查，应改成不含商务证明材料等更安全的表述。

## 交付声明

只有在临时文件存在、内容非空、独立计数和渲染验证都通过后，才能说模型稿或最终 docx 已完成。若模型任务只生成脚本、空文件或错误日志，应如实说明，改用分块重试或主 Agent 组装，并明确实际来源。
